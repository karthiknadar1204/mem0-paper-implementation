## Configuration flow

### 1. User configuration (constructor)

In `src/core/memory.js`, the `NormalMemory` constructor accepts:

```javascript
constructor(config = {}) {
  const {
    apiKey,              // REQUIRED: User's API key
    baseUrl = 'http://localhost:4000',  // Optional: Backend URL
    model = 'gpt-4o-mini',              // Optional: Model name (not used yet)
    conversationId = null,              // Optional: Existing conversation ID

  } = config;
```

Configuration is stored as instance properties:
- `this.apiKey` - Used for authentication
- `this.baseUrl` - Backend server URL
- `this.model` - Model name (stored but not actively used)
- `this.smartRouting` - Whether to use smart routing

### 2. Component initialization

After config validation, three components are created:

```javascript
// 1. HTTP Client - handles all API requests
this.client = new HttpClient(baseUrl, apiKey);

// 2. Conversation Manager - manages conversation state
this.conversationManager = new ConversationManager(this.client);

// 3. Smart Router - decides /chat vs /ask (if enabled)
this.router = smartRouting ? new SmartRouter() : null;
```

## Component breakdown

### 1. HttpClient (`src/http/client.js`)

Purpose: Makes authenticated HTTP requests to the backend.

Configuration:
- `baseUrl` - Backend URL (trailing slash removed)
- `apiKey` - Stored for authentication

How it works:
```javascript
constructor(baseUrl, apiKey) {
  this.baseUrl = baseUrl.replace(/\/$/, '');  // Clean URL
  this.apiKey = apiKey;                       // Store for auth
}
```

Key method: `request()`
- Builds full URL: `${this.baseUrl}${endpoint}`
- Adds `Authorization: Bearer {apiKey}` header
- Handles JSON serialization/deserialization
- Throws errors on failed requests

Example:
```javascript
// User calls: memory.chat("Hello")
// Internally: client.post('/conversations/123/chat', { message: "Hello" })
// Sends: POST http://localhost:4000/conversations/123/chat
// Headers: { Authorization: "Bearer sk_...", Content-Type: "application/json" }
```

### 2. ConversationManager (`src/core/conversation.js`)

Purpose: Manages conversation state and auto-creation.

Configuration:
- Receives `HttpClient` instance (needs it to create conversations)

State:
- `this.conversationId` - Current conversation ID (null initially)

Key methods:
- `ensureConversation()` - Auto-creates if missing
- `createConversation(name)` - Creates new conversation via API
- `setConversationId(id)` - Switches to existing conversation
- `getConversationId()` - Returns current conversation ID

Flow:
```javascript
// First time user calls memory.say("Hello")
await this.conversationManager.ensureConversation();
// → conversationId is null
// → Calls createConversation()
// → POST /conversations → Gets { id: "uuid-123" }
// → Sets this.conversationId = "uuid-123"
// → Now all future calls use this conversationId
```

### 3. SmartRouter (`src/core/router.js`)

Purpose: Decides whether to use `/chat` or `/ask` endpoint.

Configuration:
- No configuration needed (stateless)

How it works:
```javascript
decide(message) {
  return this.heuristicRoute(message);
  // Returns: 'chat' or 'ask'
}
```

Heuristic logic:
1. Checks question patterns (what, who, where, etc.)
2. Checks memory keywords (remember, recall, etc.)
3. Checks for question mark at end
4. Default: returns 'chat'

Example:
```javascript
decide("What do you remember about me?") → 'ask'
decide("Hi, I'm Alex") → 'chat'
decide("Tell me about my diet") → 'ask'
```

## Method flow

### `.say(message)` - Smart routing method

```javascript
async say(message) {
  // 1. Validate input
  if (!message || ...) throw new Error(...);
  
  // 2. Ensure conversation exists (auto-create if needed)
  await this.conversationManager.ensureConversation();
  
  // 3. Smart routing decision
  if (this.smartRouting && this.router) {
    const route = await this.router.decide(message);
    // route = 'ask' or 'chat'
    return route === 'ask' ? this.ask(message) : this.chat(message);
  }
  
  // 4. Fallback to chat if smart routing disabled
  return this.chat(message);
}
```

### `.chat(message)` - Direct conversation

```javascript
async chat(message) {
  // 1. Validate
  // 2. Ensure conversation
  await this.conversationManager.ensureConversation();
  const conversationId = this.conversationManager.getConversationId();
  
  // 3. Call backend
  const response = await this.client.post(
    `/conversations/${conversationId}/chat`,
    { message: message.trim() }
  );
  
  // 4. Return reply
  return response.reply;
}
```

### `.ask(question)` - Memory recall

```javascript
async ask(question) {
  // Same flow as chat, but calls /ask endpoint
  const response = await this.client.post(
    `/conversations/${conversationId}/ask`,
    { question: question.trim() }
  );
  
  return response.answer;
}
```

## Key design decisions

1. Separation of concerns: Each component has a single responsibility
2. Dependency injection: `ConversationManager` receives `HttpClient` (not created internally)
3. Auto-creation: Conversations are created automatically on first use
4. Stateless router: No cache, pure function
5. Zero dependencies: Uses native `fetch` API
6. Error handling: All errors bubble up with clear messages

The SDK is a thin wrapper that orchestrates these components to provide a simple API for users.

## Backend implementation

### Core architecture

Three main endpoints:

1. `POST /conversations/:id/chat`
   - Purpose: Conversational endpoint with immediate response
   - Flow:
     - Receives user message
     - Saves message to database
     - Fetches conversation summary + recent messages (last 20)
     - Calls LLM (gpt-4o-mini) with context for immediate reply
     - Saves assistant response
     - Queues memory extraction job (fire-and-forget, background)
     - Returns reply immediately (<600ms)
   - Response: `{ reply: "Hey Alex! Nice to meet you." }`

2. `POST /conversations/:id/ask`
   - Purpose: Pure memory recall using long-term memory
   - Flow:
     - Receives question
     - Retrieves relevant memories from Pinecone (vector search)
     - Builds prompt with memories + question
     - Calls LLM to generate answer based on memories
     - Returns answer
   - Response: `{ answer: "You live in Berlin and you're vegan.", memoriesUsed: 3 }`

3. `POST /conversations/:id/messages` (internal/legacy)
   - Purpose: Just saves message and triggers memory extraction
   - Returns: `{ status: "accepted", messageId: "..." }`
   - Note: SDK doesn't use this; it's for internal use

### Supporting endpoints

- `GET /conversations` - List all conversations for logged-in user
- `POST /conversations` - Create new conversation (with optional name)
- `POST /api-keys` - Create API key
- `GET /api-keys` - List all API keys for user
- `POST /register`, `/login`, `/logout` - Authentication

### Background workers

1. Memory processor
   - Processes messages from queue
   - Extracts facts using LLM
   - Updates Pinecone (vector DB)
   - Updates/creates/deletes memories based on LLM decisions

2. Summary processor
   - Maintains conversation summary (≤400 tokens)
   - Used in extraction prompts to avoid re-extracting old facts
   - Updates every 3 minutes per conversation

### Authentication

- Dual authentication:
  - Cookie-based JWT (for web app)
  - Bearer token API keys (for SDK)
  - Middleware checks both, prioritizes API key if present

## Design decisions

### 1. ConversationId is required
- No auto-creation
- User must explicitly pass conversationId
- Prevents accidental conversation creation
- Forces users to manage conversations intentionally

### 2. Smart routing
- `.say()` automatically routes
- Heuristic-based (fast, zero cost)
- Can be disabled with `smartRouting: false`

### 3. Dual authentication
- Cookie-based for web app
- API key for SDK
- Same middleware handles both

### 4. Background processing
- `/chat` returns immediately
- Memory extraction happens in background (1-4 seconds)
- User gets instant response, memory updates later

### 5. Zero dependencies (SDK)
- Uses native `fetch`
- No external libraries
- Small bundle size
